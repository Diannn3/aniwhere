# AniWhere farmer-first UI/UX audit — 20 September 2026

**Decision (updated 21 September):** acceptance is **not yet verified**. The implementation has received an independent source re-review, team-run technical checks, and targeted browser checks across four phone widths. These establish substantial progress, but they do not replace farmer sessions, TalkBack/device testing, or measured weak-network performance. No farmer interviews or device tests are represented as completed.

## Scope and evidence

The inspected production baseline is `bdc9881e8269f5f9e1e2ea19894877cebcea99f7` on `main`. The local implementation branch is `codex/farmer-uiux-audit`. The product is a **pre-transaction decision aid**: a match indicates compatibility with recorded terms, never a reservation or guaranteed purchase. Fictional fixtures are the runtime data; the Supabase files are an undeployed scaffold. The map is illustrative and distances use Haversine straight lines. These boundaries are explicit in the [README](../README.md), [frontend limitations](FRONTEND_LIMITATIONS.md), [trust-model report](ANIWHERE_TRUST_MODEL_V2_IMPLEMENTATION_2026-09-18.md), [distance helper](../src/lib/domain/distance.ts), and [demo offers](../src/content/demo-offers.ts). Scoring anchors: 1–3 unusable, 4–6 substantial friction, 7 dependable with minor friction, 8–9 polished and validated, 10 exceptional with strong evidence. An implementer cannot be the only post-change approver.

Targeted browser checks support the primary layout and selected recovery paths. ## Regression and measurement protocol

1. Pin the implementation SHA and production-build configuration. Run `pnpm test`, `pnpm check`, `pnpm build`; record exit codes and failures, not just a claim of “tested.” Preserve the currently passing domain semantics and add targeted regressions for F01–F07.
2. On 320, 360, 390, and 412px widths, walk the farmer path with **250 kg calamansi from Santa Cruz**, a fixed ready date, and optional details. Switch Filipino ↔ English; visit discovery, two details, saved, compare, Back, and refresh. Add a third outlet, remove one, revisit details, and verify selections and hauling values.
3. Exercise full, partial, unknown-capacity, unsupported-crop, missing-price, missing-transport, and expired-offer cases. Distinguish a fixed September 2026 scenario from current-date behavior. Check every amount against the accepted quantity and the formula `accepted kg × posted price − entered/known hauling`; explain that farm production costs are excluded.
4. Disable storage and clipboard writes. Test malformed stored values, empty results, invalid shared URLs, interrupted navigation, browser Back, and reload. Verify each status message against the actual operation.
5. Run keyboard-only and TalkBack checks on an Android device. Include dialog focus, control names/states, text at 200%, software keyboard overlap, long Filipino copy, and responsive tablet/desktop checks. Record any serious or critical automated accessibility findings and manual exceptions.
6. On each core route, record three **cold** lab runs with about 1.6 Mbps down, 750 Kbps up, 150 ms latency, and 4× CPU slowdown. Record device/tool version, LCP, CLS, interaction response, compressed required JS, and variability. Targets: median LCP ≤2.5s; CLS ≤0.1; tested interactions ≤200ms; gzip JS home <75 KiB, list discovery <120 KiB, fully usable map <300 KiB. A lab interaction result is not field INP. Supplement with a budget Android phone, blocked external fonts, weak data, and interrupted connection. Distinguish already-loaded behavior from offline reload; offline reload is not promised.

### Observed farmer sessions: facilitator script

Recruit **3–5 farmers** with varied smartphone familiarity. Use their preferred language; provide a budget Android phone with ordinary mobile data. Obtain permission to record notes. In individual 20–30 minute sessions, say: “This shows sample information. Please think aloud. I will not guide you through the screens.” Give a consistent harvest scenario or ask them to enter a realistic one, and record which was used. Do not coach, explain labels during a task, send a message, or contact a buyer.

| Task | Neutral prompt | Observe and record |
|---|---|---|
| Enter and search | “Enter your harvest and find two places you would contact.” | Unassisted completion, wrong input, hesitation, help requested, time |
| Explain partial fit | “Which place could take only some of the harvest? How much remains?” | Whether capacity is understood as recorded, not guaranteed |
| Explain money | “What does the amount after transport include and leave out?” | Confusion with profit, price status, or unknown hauling |
| Identify uncertainty | “What would you confirm before travelling?” | Recognition of demo data, offer freshness, capacity, terms |
| Save and prepare | “Save one option and prepare a message you could send.” | Whether save persists, copied text is understood, no mistaken belief a message was sent |

After each task, ask “What did you expect to happen?” and “What would you do next?” Capture exact participant language when consented, with anonymous IDs only. For each task report numerator/denominator, e.g. `4/5 unassisted`, plus errors, help, hesitation, and quote/theme. **At least 80% unassisted per core task** is required, with the raw counts shown. A recurring belief that a match guarantees purchase, demo prices are live, or after-transport proceeds equal profit blocks acceptance until corrected and retested. Agents and mockups cannot substitute for farmers.
